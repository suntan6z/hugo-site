# Forms & Email

Both forms on the site submit via JavaScript `fetch()` calls to a **Scaleway Function** (`functions/`), which relays the request to **Resend** for actual email delivery / subscriber storage. Scaleway is a French cloud provider — chosen deliberately over Cloudflare/AWS/etc. so the relay layer stays under EU jurisdiction, consistent with the rest of the site's EU-hosted services (StaticHost.eu, self-hosted Litlyx).

- **Contact form** — markup lives in `content/contact.md`; the submit handler (`POST` to the `contact` function's URL) is in `static/js/main.js`, handled server-side by `functions/contact.js`. The frontend sends `firstName`/`lastName` as separate fields (not pre-joined), so both templates can show them individually, the dropdown's `subject` key plus, for "Other", the sender's own `customSubject` (the function turns the key into its label, or the description, for the email's subject line), and the `altcha` proof of work (below). On a valid submission it sends **two** emails via Resend, both templated to match the site's palette (cream background, dark-rose accent, serif heading): the internal notification to `contact@loconsole.eu` (Resend Template `contact-form-notification`, variables `first_name`/`last_name`/`email`/`phone`/`subject`/`message`, each field clearly divided in its own row), and a templated auto-reply confirmation to the submitter (Resend Template `contact-form-confirmation`, variables `name`/`subject`/`message_preview`). The confirmation send is best-effort — a failure there doesn't fail the request, since the notification reaching `contact@loconsole.eu` is what actually matters.
- **Newsletter signup** — markup in `layouts/blog/single.html`, submit handler in `static/js/main.js`, handled server-side by `functions/newsletter.js`. It is **double opt-in**: `POST {email, lang, altcha}` adds nobody. It checks the proof of work, looks the address up (an address already on the list gets the same answer and no email, so the form cannot be used to find out who is subscribed) and sends a confirmation email in the page's language with a link to `/<lang>/newsletter-confirm/#<token>`. The token is the address and an expiry (48 hours) signed with `CONFIRM_SECRET`, so there is no pending list to keep. That page's script (`main.js`) posts `{confirm: token}` back; a valid token adds the address and sends the welcome email, and using a link twice is harmless. Putting the token after the `#` keeps the address out of server logs and analytics, and the page acts on it only when its own script runs, which a mail scanner that merely fetches the link does not do. When the address is added, it goes to the single Resend Audience that currently exists in the account ("General", `RESEND_GENERAL_AUDIENCE_ID` — a hardcoded constant in `newsletter.js`, not a secret, just a resource ID) via `POST https://api.resend.com/audiences/{id}/contacts` — the audience-scoped endpoint, not the flat `POST /contacts` one. (The flat endpoint accepts an `audienceId` body field but silently ignores it — verified directly against the API: it returns `201` and creates a contact, but never actually enrolls it in the named audience. This was true even for a valid audience ID, so the original code's audience-enrollment likely never worked correctly.) Since that endpoint's create call is an idempotent upsert (always `201`, even for an existing contact), `newsletter.js` does a `GET /audiences/{id}/contacts/{email}` first to check whether this is a genuinely new subscriber before deciding to send the welcome email (Resend Template `newsletter-welcome`, best-effort). There used to be a second "Blog" audience referenced in the old Supabase code — that audience has since been deleted from the Resend account, so it's not used here.
- **Both forms require an ALTCHA proof of work** (`GET <function>?challenge=1` hands out a signed challenge; the visitor's browser solves it in the background, usually before the form is filled in; each solution works once). The server half is `functions/lib/altcha.js`, with no dependencies, using the same protocol as the official widget (vendored in `static/js/altcha/`) and checked against `altcha-lib` in both directions. Both functions also refuse a POST whose `Origin` is not the site's. The honeypot field `website` stays. Secrets: `ALTCHA_SECRET` signs challenges and `CONFIRM_SECRET` signs confirmation links; `deploy.sh` sets both on the namespace next to `RESEND_API_KEY` (any long random string: `openssl rand -hex 32`), and the deploy workflow reads them from GitHub secrets of the same names.
- Both functions have a basic in-memory per-IP rate limit (3 requests/60s, see `functions/lib/rateLimit.js`) — resets on cold start since Scaleway scales to zero, so it's weaker than persistent rate limiting would be, but still blunts rapid-fire abuse within a warm instance.
- CORS is a small hardcoded allowlist in `functions/lib/cors.js`: `https://lorenzo.loconsole.eu` (production) and `http://localhost:1313` (local Hugo dev server).

`functions/` is a separate deployable unit from the Hugo site: StaticHost only ever runs `hugo --minify` (per `statichost.yml`) and never touches it. Deploy with `functions/deploy.sh` (requires the `scw` CLI configured, plus a `RESEND_API_KEY` env var — see `functions/.env.example`). It also runs automatically via `.github/workflows/deploy-functions.yml` on pushes to `main` that touch `functions/**`.

The two functions have **no npm dependencies at all** — they use Node 22's built-in `fetch` and `node:crypto` and nothing else, so there's no `node_modules` to audit or ship. `cd functions && npm test` runs their tests (`node --test`, also dependency-free). `functions/dev-server.js` is a tiny local test harness: `ALTCHA_SECRET=dev CONFIRM_SECRET=dev FAKE_RESEND=1 node dev-server.js contact 8787` (or `npm run dev:contact` / `dev:newsletter`), then `curl` it. `FAKE_RESEND=1` answers Resend from memory and prints what would have been sent; `DEV_PAGE_ORIGIN=http://localhost:1315` makes it accept a Hugo server on another port. Without the two secrets the forms refuse every submission, as they would in production.

The Resend API key, `ALTCHA_SECRET` and `CONFIRM_SECRET` are the namespace secrets needed on Scaleway (set via `deploy.sh`, which calls `scw function namespace create/update`) — it never appears in this repo or in the shipped frontend JS. This is a meaningful difference from the old Supabase setup: previously the Supabase anon key was public-by-design in the client JS (that's how Supabase Edge Functions are meant to be called), while the actual Resend key was hidden inside the Supabase function. Now there's no equivalent public key needed at all — the frontend calls the function with no `Authorization` header, and Scaleway is the only place that ever sees the Resend key.

Each function gets its own auto-generated HTTPS URL on first deploy (of the form `https://<name>-<slug>.functions.fnc.<region>.scw.cloud`) — there's no custom domain involved, which avoids having to point `loconsole.eu`'s DNS at Scaleway. After running `deploy.sh`, if a URL changed paste it into `FORM_ENDPOINTS` at the top of `static/js/main.js` and into the `connect-src` of `static/_headers`, which names both hosts exactly.

The Resend Templates referenced by ID (`contact-form-notification`, `contact-form-confirmation`, `newsletter-welcome`) are managed in the Resend dashboard (Templates section), not in this repo — editing their content/design there takes effect immediately without any redeploy here. There's also a `contact-form-reply` template in Resend, but that one is a manual draft for composing replies by hand — it's not referenced by any code here.

To change the backend logic (e.g. swap Resend for another provider, or adjust validation), edit `functions/contact.js` / `newsletter.js` and re-run `functions/deploy.sh` (or push to `main`, which triggers the same via CI, or run the workflow by hand: a big commit can skip the path filter).

If you add any new external endpoint here, also update the CSP `connect-src` directive in `static/_headers` or the request will be blocked in production.

## Checking they still work

The portal's dashboard runs the same CORS preflight a browser makes before submitting either form, and checks the answer allows the site's origin — so a silently broken contact form shows up there rather than in a message that never arrives. These functions scale to zero, so a first check after a quiet spell can report the container waking up ("was asleep") rather than a fault.

**The subscriber list can be downloaded** from the portal (Newsletter → Subscribers → *Download as CSV*): address, whether they are still subscribed, and when they joined. It is read fresh from Resend, every page of it, and it is the one copy of the list that is in no repository. The same file answers someone who asks what is kept about them.

**Newsletter broadcasts** are separate from the signup handler above: the portal talks to Resend directly, with its own key, and sends to the same audience this signup form fills. See the portal's **Newsletter** page: pick a published article, write the email beside a live preview (desktop or phone width), optionally send yourself a test copy, then review the checks and confirm in a dialog. Nothing is sent before that last confirmation, and it cannot be recalled. At the last step you can instead pick a later morning: it goes out at 9:30 Paris time (once the site is live) and can be cancelled from the **Sent** tab until then. That tab shows, for the latest five broadcasts, how many were delivered, bounced, marked as spam and unsubscribed, read from Resend's per-recipient lists when the tab is opened. Opens and clicks appear only if Resend recorded any, which needs tracking switched on for the sending domain; the privacy policy says they are not tracked, so leave it off unless the policy changes too. Each broadcast also links to its page in Resend.
