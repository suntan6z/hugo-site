# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Personal website for Lorenzo Loconsole, built with **Hugo v0.165.0 extended** (pinned exactly — see Deployment). Hand-written templates and CSS — no external Hugo theme. Live at [lorenzo.loconsole.eu](https://lorenzo.loconsole.eu).

## Commands

```bash
hugo server          # dev server with live reload at http://localhost:1313
hugo --minify        # production build (rarely run by hand — see Deployment)
```

There are no tests, linters, or a build toolchain beyond Hugo itself for the site proper, apart from `node scripts/image-metadata.mjs [--fix]` (see "No image is published with metadata" below). `functions/` (the Scaleway Functions backing the forms) is a separate, dependency-free Node project deployed via `functions/deploy.sh` — see `docs/forms-and-email.md`; its tests are `cd functions && npm test` (`node --test`, no install needed). `admin/` is the content portal, a separate Node project with its own tests — see **The admin portal** below.

## Deployment

Hosted on **StaticHost.eu**, which watches the GitHub repo: push to `main` and StaticHost runs the build on its own servers and serves the result. No CI deploys the Hugo site. `.github/workflows/hugo-build.yml` does *build* it on every push, with the exact image and command read from `statichost.yml`, as an early warning — it deploys nothing. The other workflows are scoped to `functions/**` and `admin/**` and never touch the site.

**The Hugo version StaticHost uses is pinned explicitly in [`statichost.yml`](statichost.yml)** (repo root), not in StaticHost's dashboard. That file's presence makes StaticHost ignore its own dashboard "Hugo/Version/Build flags/Public directory" fields entirely — they become inert once `statichost.yml` exists. This was deliberate: StaticHost's dashboard version field is "hidden state" that isn't visible in the repo and silently drifted out of sync with local dev once (StaticHost defaulted to Hugo 0.150.0 while local dev was on 0.163.3, which broke the build the moment a template used an API introduced after 0.150 — `hugo.Sites`/`hugo.Data`/`.Language.Label`/`locale`+`label` config keys, all added in Hugo 0.156–0.158). Keeping the version in `statichost.yml` means it travels with the repo and is visible in `git blame`.

**Image tag note:** `hugomods/hugo` (the Docker image family `statichost.yml` references) only publishes its convenient bare `ci-X.Y.Z` alias for a curated subset of releases — it did **not** have one for 0.163.3 at the time of writing. The full ingredient-tag (e.g. `debian-git-0.165.0`, used in `statichost.yml`) exists for every release instead. Per hugomods' own docs (docker.hugomods.com/docs/tags/): tags **without** a `std`/`reg` prefix are the Hugo **extended** edition (needed here for `.Resize` to webp on the hero image, matching the local `+extended` Hugo binary); `std`/`reg`-prefixed tags are the **non-extended** standard edition — don't swap these casually. When bumping the pinned version, search https://hub.docker.com/r/hugomods/hugo/tags for a matching `git-<version>` tag (no `std`/`reg` prefix) rather than assuming one exists.

A local `hugo server`/`hugo build` succeeding does not, by itself, guarantee the StaticHost build succeeds. **Local Hugo drifts ahead of the pin** — it comes from Homebrew (0.168.0 at the time of writing, against the pinned 0.165.0), and hugomods doesn't publish an image for every release (none for 0.166.0, three days after that release), so exact parity can't be kept by hand. `hugo-build.yml` closes the gap instead: it runs the pinned image in GitHub Actions, so a template relying on a newer Hugo fails there with a readable log. Check that workflow after changing templates or `hugo.toml`.

**Never commit `public/` or `resources/`** — both are git-ignored. StaticHost regenerates them on every deploy; tracking them causes build conflicts. The repo holds **source only**.

## Architecture — the non-obvious parts

**`static/` and `assets/` follow Hugo's default convention** — no custom `[module.mounts]`. `static/` holds everything copied verbatim to the site root: CSS (`/css/main.css`), JS, fonts, `/cv-fr.pdf`, `/_headers`, the root `/404.html`, and most images under `/img/...`. `assets/` holds only the handful of files actually processed through Hugo Pipes — currently just `assets/img/hero.webp` and `hero.jpeg` (same photo; the JPEG is the `<picture>` fallback for browsers without WebP support, and the source for the JPEG used in `og:image`/JSON-LD), both resized via `resources.Get` + `.Resize`. Reference root-copied files by their served path (e.g. `/img/logo.svg`); only reach for `resources.Get`/`resources.Match` when a file actually needs Pipes processing — otherwise it belongs in `static/`.

**Blog posts are page bundles.** Each article is `content/blog/<slug>/index.md` with its images in the same folder. Because the section is `blog`, these render through `layouts/blog/single.html` (article) and `layouts/blog/list.html` (the `/blog` index). The bundle's images are page resources, which the image render hook (below) uses to emit real dimensions.

**Gallery photos are headless page bundles, not assets.** Each city is `content/gallery/<city-slug>/index.md` (plus `content/gallery/_index.md` for the section) with its photos co-located as page resources — same pattern as blog bundles, but every one of these has `build: { render: never, list: never }` in front matter, so Hugo never generates an HTML page for them or lists them anywhere (no `/gallery/` page, nothing in the sitemap). The photo *files* still get published to `/gallery/<city-slug>/<file>` as normal page resources. `layouts/index.html` reads `data/gallery_cities.json` for the list of slugs and calls `.Site.GetPage "/gallery/<slug>"` directly (`GetPage` works on headless pages even though `.Pages` traversal would skip them since `list: never`), then iterates `.Resources.ByType "image"`; display order comes from the numeric prefix of each filename. The folder name must still match a `slug` in `data/gallery_cities.json` (those drive the filter pills). `data/gallery_photos.json` is optional and only overrides `caption`/`alt_text`, keyed by the photo's served `image_url`. Each photo is sent at three AVIF sizes plus the original: `strip_url` (a 544×704 crop for the strip), and in the lightbox `preview_url` (480px, shown instantly, blurred) → `full_url` (fits 1920px) → `image_url`, the original, loaded only when the visitor zooms in or the screen needs more than 1920px. The three copies are published with `resources.Copy` under readable names, `/gallery/<city>/<city>-<NN>-{strip,480,1920}.avif`, instead of Hugo's hashed `_hu_` names, and the lightbox's "Download original" button saves `image_url` as `<city>-<NN>.<ext>`. Each level is swapped in only once decoded, in a box sized from the photo's shape (`w`/`h`), so nothing jumps. `image_url` is also the key the overrides file and the portal use. The photo array is serialized to JSON and the whole gallery (pills, strip, lightbox) is rendered client-side.

**Thumbnail / social-card image resolution lives in shared partials** — `layouts/partials/resolve-image-src.html` (resolves a front-matter value to a page-resource or pass-through URL) and `layouts/partials/first-content-image.html` (first `<img src>` in rendered `.Content`, via `findRE`) compose into `layouts/partials/resolve-thumb.html` (featured_image, else first content image). Change the rule in one of these three files, not at the call sites. They return a URL; `layouts/partials/image-variant.html` turns that URL into a resized copy when it is one of the page's own bundle images (it never decides *which* image).
- `layouts/blog/list.html` — thumbnail on the `/blog` grid, via `layouts/partials/card-thumb.html` (`resolve-thumb.html` + a 224px crop, or a category-icon placeholder for image-less posts).
- `layouts/_default/baseof.html` — `og:image` / `twitter:image` for link previews, via `resolve-thumb.html`; falls back to `static/img/logo-og.png` — the logo composited onto the site's cream background at 1200×630 — for the homepage and image-less pages.
- `layouts/index.html` — homepage "Latest Articles" grid, via `card-thumb.html` (same).
- The first image is only the **default**: choosing any other bundle image must stay possible. The editor's Images panel sets `featured_image` ("Use as thumbnail"), using the same rule mirrored in `admin/src/lib/thumbnail.ts`, which also picks the newsletter picture.
- `layouts/blog/single.html` — the article's own featured image and the Erasmus+ partner logo also go through `resolve-image-src.html`.

**Image render hook** (`layouts/_default/_markup/render-image.html`) rewrites every Markdown image: page-bundle images are resolved as page resources to emit intrinsic `width`/`height` (prevents CLS), `loading="lazy"` and a `srcset` of 480/960/1600px WebP copies; `src` stays the original file, because `first-content-image.html` reads it back as the default thumbnail. External/root-relative images fall back to a plain lazy `<img>`.

**No image is published with metadata** (EXIF camera data and dates, GPS position, IPTC/XMP, comments, appended iPhone gain maps) — three layers, one definition of "clean" in `admin/src/lib/server/content/image-metadata.ts` (lossless: drops JPEG segments / PNG and WebP chunks, keeps pixels and the ICC colour profile):
- the portal strips every image in every commit (`withoutMetadata` in `content/repo.ts`), on top of the browser's canvas re-encode;
- `layouts/partials/image-metadata-guard.html` (called from the homepage) **fails the Hugo build** — on StaticHost too, so nothing is published — if any bundle or `assets/` image still carries metadata;
- `node scripts/image-metadata.mjs` checks `content/`, `static/` and `assets/` (CI runs it in `hugo-build.yml`, since Hugo never looks inside `static/`); `--fix` cleans files in place, first rotating sideways phone photos upright with `jpegtran` (lossless; `brew install jpeg-turbo`), since dropping their EXIF rotation flag alone would leave them sideways.

Because of that, every committed original is stored upright, and templates resize without any EXIF-orientation step. Image processing is still the bulk of a cold build (~75 s locally, more on StaticHost, which keeps no cache between deploys), dominated by decoding the multi-MB originals committed before the portal resized uploads.

**Categories are not real taxonomy.** `hugo.toml` sets `disableKinds = ["taxonomy", "term"]`, so `/categories/` pages are never generated. `category` front matter is just a label that the client-side JS filter on `/blog` uses. Valid values: `Technology`, `Cybersecurity`, `Personal`, `Erasmus+` — keep these exact English values in front matter regardless of the file's language; the visible label is localized via `layouts/partials/category-label.html` (see Multilingual). `Erasmus+` additionally triggers a partner strip in `layouts/blog/single.html`, which needs extra front matter (`partner_name`, `partner_url`, `partner_logo_url`, optional `project_url`, `eu_funding_text`).

**SEO/meta is centralized** in `layouts/_default/baseof.html`: canonical URL, Open Graph + Twitter cards, and JSON-LD (`Person`/`WebSite` on the homepage, `BlogPosting` on articles). Sitemap, RSS (`/blog/feed.xml`), and robots are custom output formats configured in `hugo.toml` (`[outputs]`, `[outputFormats]`).

**Forms POST to Scaleway Functions** (`functions/` — contact form handler in `static/js/main.js`, markup in `content/contact.md` rendered via `layouts/_default/single.html`; newsletter signup markup + handler both in `layouts/blog/single.html`). Scaleway (a French cloud provider) was chosen deliberately to keep this relay layer under EU jurisdiction, matching the rest of the site's EU-hosted services. The functions are a separate deployable unit from the Hugo build, deployed via `functions/deploy.sh` and its own scoped GitHub Actions workflow (`.github/workflows/deploy-functions.yml`, triggered only by changes under `functions/**`) — StaticHost never touches it. The Resend API key lives only as a Scaleway namespace secret (set by `deploy.sh`), never in this repo or in shipped JS; the frontend calls the functions with no auth header at all. Each function gets its own auto-generated `*.functions.fnc.<region>.scw.cloud` URL on first deploy — see `docs/forms-and-email.md` for the full picture. To change the backend, edit `functions/contact.js` / `newsletter.js` and re-run `functions/deploy.sh` (or run **Deploy Scaleway Functions** by hand from the Actions tab: GitHub only compares the first 300 changed files against a workflow's `paths`, so a big commit can skip it silently), or change `FORM_ENDPOINTS` at the top of `static/js/main.js` to point elsewhere entirely — the one place the two URLs live on the site, also named in the CSP.

**Both forms carry an ALTCHA proof of work, and the newsletter is double opt-in.** The widget is vendored unmodified in `static/js/altcha/` (see its README for the version and how to update) and loaded as a `type="module"` script, because as a classic script its one-letter top-level names collide with the page's. It sits *next to* its form, never inside it: inside, its hidden required checkbox blocks submitting while it works. `static/js/main.js` ("ALTCHA") starts it on the form's first focus, waits for it on submit and spends each answer once. The server half is `functions/lib/altcha.js` (the protocol of altcha-lib 2.x, PBKDF2/SHA-256, written against `node:crypto` and cross-checked against the real library in both directions); challenges are stateless and signed with `ALTCHA_SECRET`, and only the list of already-spent solutions is kept, in memory, per warm instance. Subscribing sends a confirmation email whose link is `/<lang>/newsletter-confirm/#<token>` (signed with `CONFIRM_SECRET`, 48 hours, address inside; after the `#` so it reaches no log or analytics); the page's script posts the token back and only then is the address added and the welcome email sent (`functions/lib/confirm.js`, `confirm-email.js`). The privacy policy says exactly this, so change them together. `functions/dev-server.js` has `FAKE_RESEND=1` and `DEV_PAGE_ORIGIN` for trying the forms locally without sending email.

**`redirect` content type pins a meta-refresh at an exact old URL.** A file in `content/redirects/` sets `type: "redirect"`, a `url:` front matter override (bypasses language-prefixing, forcing the page to that exact path) and `redirect_to:`; `layouts/redirect/single.html` renders the meta-refresh + JS. `build.list: false` keeps it out of the sitemap and the client-side search index, and the section's `_index.md` is `render: never` / `list: never` so the folder itself is never a page. It exists because StaticHost's deploy doesn't prune files no longer in a build's output: a URL that stops being produced keeps serving its old content at 200 instead of 404ing.

**When a redirect is needed, and when it is not.** `static/404.html` already bounces any path *missing* a language prefix to `/en/<path>`, and deliberately leaves `/en/…`, `/fr/…`, `/it/…` alone. So bare pre-`/en/` URLs need no files — the 15 `content/legacy-*.md` stubs that used to cover them were deleted once that was verified (Bing reported no traffic on them, and the already-deployed copies keep redirecting anyway since nothing prunes). Language-prefixed URLs are the opposite case: the 404 fallback won't touch them, so **renaming an article writes one redirect per language** (the portal does this automatically — see The admin portal below).

**Security headers live in `static/_headers`** (served by StaticHost). The CSP `connect-src` names the two Scaleway Functions hosts exactly (they change only if a function is recreated — then `FORM_ENDPOINTS` in `main.js` and this line change with them) and the analytics host — **if you add any external fetch/connection, update the CSP there** or it will be blocked in production. Analytics (Litlyx) only loads when `not hugo.IsServer`, so it never runs in the dev server.

## Multilingual (EN / FR / IT)

The site is trilingual — **English (default), French, Italian** — using Hugo's native multilingual mode with **translation by filename**. Config lives in the `[languages]` block of `hugo.toml`.

- **URLs:** `defaultContentLanguageInSubdir = true`, so every language sits under its own prefix, including English (`/en/blog/...`), French (`/fr/...`), and Italian (`/it/...`). This is required for Hugo's automatic `sitemapindex.xml` — when English instead lived at the root, its own per-language `sitemap.xml` collided with the auto-generated index at that same root path. Root `/` is a meta-refresh redirect to `/en/`; `static/404.html` handles old pre-`/en/` links generically (see the `redirect` content type below).
- **Per-language vs shared config:** language-varying settings (just `description`) live under `[languages.<lang>.params]`; the nav menu lives under `[languages.<lang>.menus.main]` using `pageRef` (so links auto-prefix the language). Everything else, including `quote` (a direct Snowden quote, deliberately not translated), stays in the shared top-level `[params]`. Each language also sets `locale` and `label` (these replaced the deprecated `languageCode`/`languageName`).
- **Translating a page = one Markdown file per language, same folder.** English keeps its plain name; add `.fr.`/`.it.` siblings. Blog post: `content/blog/<slug>/index.md` + `index.fr.md` + `index.it.md`. Standalone page: `content/about.md` + `about.fr.md` + `about.it.md`. Section index: `_index.md` + `_index.fr.md` + `_index.it.md`. Co-located **images are shared** across all language versions of a bundle — never duplicate them. Hugo auto-links same-folder/same-basename files as translations. A missing translation simply doesn't render in that language (the switcher falls back to that language's home, and a `pageRef` menu entry pointing at an untranslated page renders an empty `href`).
- **Gallery needs per-language stubs.** Because `layouts/index.html` resolves each city via the *current* language's `.Site.GetPage "/gallery/<slug>"`, every city bundle (and `gallery/_index.md`) has `index.fr.md` / `index.it.md` stubs — identical front matter, since the photos and `data/*.json` are language-neutral and shared. Add the same two stubs whenever you add a new gallery city, or the strip is empty on `/fr/` and `/it/`.
- **UI strings live in `i18n/{en,fr,it}.toml`**, referenced with `{{ i18n "key" }}`. Keys are **case-sensitive**; add every new key to all three files. Client-side JS strings (search modal in `header.html`, gallery in `index.html`, the newsletter box's labels in `blog/single.html`) are injected into a `window.I18N` object via `(dict … | jsonify | safeJS)` — **the `safeJS` is required**; without it Go's html/template double-encodes the JSON into a string and `Object.assign` spreads it character-by-character.
- **Category labels are localized, category *keys* are not.** `.Params.category` stays the canonical English value (`Technology`, `Erasmus+`, …) used by the JS filter; the visible label is rendered through `layouts/partials/category-label.html`, which maps the value to `i18n "cat_<value>"`. Filter pills keep English `data-category`/onclick args and only translate the button text.
- **Dates** use `{{ .Date | time.Format ":date_long" }}` (article) or `":date_medium"` (cards, search) so they localize via each language's `locale`. Never hardcode a `"Jan 2, 2006"` layout.
- **SEO** (`baseof.html`): `<html lang>`, `og:locale` (+ `og:locale:alternate`), JSON-LD `inLanguage`, and `hreflang` alternates (incl. `x-default` → English) are all derived by looping `.AllTranslations`. The language switcher (`header.html`) links each language to the current page's translation, falling back to that language's home via `.Site.Home.AllTranslations`.
- **English-only by design:** the `404.html` copy and the contact-form validation strings in `static/js/main.js` are not translated. The newsletter confirmation page (`content/newsletter-confirm*.md`, `noindex`, `build.list: never` so it stays out of the sitemap and search) and the confirmation email (`functions/lib/confirm-email.js`) are written in all three.

## Adding content

Articles are normally written in the admin portal (see below), which produces exactly what follows. By hand: `hugo new blog/my-slug/index.md` (uses `archetypes/blog.md`, starts `draft: true`). Set the lead image as the first Markdown image in the body (becomes the thumbnail everywhere, the social card and the newsletter picture), or set `featured_image` in front matter only to pick a different one. To translate it, add `index.fr.md` / `index.it.md` in the same bundle (see Multilingual). Site-wide settings: title, social links (also editable from the portal's Settings), hero photo and résumé URL are in `hugo.toml` under the shared `[params]`; the homepage quote, meta description and nav menu are **per-language** under `[languages.<lang>]`.

## The admin portal (`admin/`)

A SvelteKit app at **admin.loconsole.eu** (Scaleway Serverless Container) for writing and publishing without a code editor: article editor with preview, autosave and DeepL first drafts for FR/IT, click-to-edit on the real page for the standalone pages (About, Contact, Privacy), with an HTML view for what clicking cannot reach, a structured editor for the Now page (rows with logos, cover, archive by year), version history with restore for all of them, gallery manager, a Library of every picture on the site with what uses it (unused ones can be deleted, any can be replaced under the same name), a ⌘K / Ctrl+K search palette over screens, articles, pages, cities and interface strings (`lib/search.ts` ranks in the browser; `/api/search` supplies the list), UI-strings editor, site settings (homepage quote, per-language descriptions, hero photo, CV, social links), redirect management, newsletter broadcasts and subscribers (Resend; a four-step flow — article, write with live preview, test copy, review and confirm in a dialog), visitor numbers (self-hosted Litlyx: pages, sources, devices, campaigns, time on page, live visitors), Bing and Google Search Console stats with crawl health, newsletter results (delivered, bounced, unsubscribed) per broadcast, "Is it on Google?" and PageSpeed on each published article, SEO pre-flight, a weekly outside-link check, a daily health check (site, forms, certificates) and IndexNow. Hugo ignores the directory. Deployment, secrets and recovery: [`admin/DEPLOY.md`](admin/DEPLOY.md).

**It writes to this repo; it is not a CMS database.** Each save is one commit to `main` via a GitHub App (Git Data API: blobs → tree → commit → fast-forward ref, never force), and StaticHost builds it like any push. Work in progress is autosaved to object storage, not committed. Two consequences: expect commits authored by the app, and **any push touching only `admin/` still costs a StaticHost build** (StaticHost can't path-filter), so batch portal changes.

```bash
cd admin
npm run dev               # http://localhost:5180 — LOCAL MODE: saves edit this working tree directly
npm test                  # unit tests, incl. a front-matter round-trip over every real content file
npm run test:integration  # builds, boots the real app against a throwaway copy of the site, drives it over HTTP
npm run check             # types (a Vite build does not fail on type errors)
```

Local mode (no GitHub App configured) reads and writes the working tree and keeps state in `admin/.state/`; `ALLOW_DEV_LOGIN=1` in `admin/.env` skips the passkey. Saving an article in local dev really changes `content/` — review `git diff` before committing.

**How the server code is laid out, and why.** Every hard piece of logic lives in a **pure module** — no `$env`, no repo, no network — paired with a thin module that does the talking:

| pure (unit-tested directly) | does the I/O |
|---|---|
| `content/frontmatter.ts`, `content/rename.ts`, `diff.ts` | `content/post.ts`, `content/repo.ts` |
| `content/gallery-data.ts` | `content/gallery.ts` |
| `integrations/bing-parse.ts` | `integrations/bing.ts` |
| `src/lib/newsletter-email.ts` | `integrations/resend.ts` |
| `translate/markdown-xml.ts` | `integrations/deepl.ts` |
| `seo/rules.ts` | `seo/preflight.ts` |
| `auth/access.ts`, `auth/ratelimit.ts` | `auth/session.ts`, `auth/state.ts` |
| `content/revisions.ts` | `content/repo.ts` (`history`, `readTextAt`), `content/history.ts` |
| `content/redirects.ts` | `routes/(app)/redirects` |
| `content/site-params.ts`, `content/site-files.ts` | `routes/(app)/settings` |
| `seo/links.ts`, `tasks/edits.ts` | `integrations/linkcheck.ts`, `tasks/session.ts` |
| `integrations/litlyx-parse.ts` | `integrations/litlyx.ts` |
| `integrations/resend-stats.ts` | `integrations/resend.ts` (`broadcastStats`) |

That is why `npm test` can drive front-matter serialisation, machine-translation round-trips, the diff, the SEO rules and the access allow-list with no key, no network and no build step — SvelteKit's `$env` cannot even be imported by the plain Node test runner, so a pure module that starts importing it breaks its own tests immediately. **Keep new logic on the pure side and let the thin module pass it data.** Site-wide values that several domains need (`langs.ts`) sit at the root of `lib/server/`, not inside one domain folder. The pure modules the **browser** also runs (`pages.ts`: page checks and "last updated" stamps; `thumbnail.ts`; `newsletter-email.ts`, whose output is the newsletter wizard's live preview) sit in `src/lib/` instead, because SvelteKit refuses to bundle anything under `lib/server/` into client code.

**Contracts between the site and the portal** — change one side, check the other:
- **Front matter is edited line by line, never re-serialised** (`admin/src/lib/server/content/frontmatter.ts`), preserving comments, key order and trailing newlines. Output must start with `---\n` at byte 0 or `layouts/partials/auto-untranslated-pages.html`'s regex silently stops generating the FR/IT placeholder pages. The round-trip test reads `content/blog/**` and `content/gallery/**` directly, which is why content changes also run the admin test workflow.
- **`layouts/index.buildinfo.json` → `/en/build-info.json`** is a content manifest the portal polls to tell when a commit is live. Keep the `BUILDINFO` output format in `hugo.toml`.
- **The category list is duplicated** in `CATEGORIES` in `frontmatter.ts` (see Categories above).
- **The standalone pages (except Now) are hand-written HTML**, edited by clicking text on the rendered page (`PageVisualEditor.svelte`), never through the Markdown editor. Each click-editable *block* (heading, paragraph, list item, leaf `div`, link or button — made only of text and inline markup, with no `id` inside) is found by its offsets in the source by `admin/src/lib/page-blocks.ts`, and an edit replaces only that block's inner HTML, so the saved file differs from the old one in exactly the lines touched; nothing is re-serialised from the browser DOM. Pictures are edited by their attributes, never their content: alt text is patched into the `<img>` tag, and "Replace" writes a new file under the same name through `POST /api/media` (only files in `static/img/`). What is not a block (structure, forms, icons, text a script writes itself) is reached through the editor's "HTML (advanced)" view, the textarea with a preview. Contact's form is driven by `static/js/main.js` by element id; the ids it needs are duplicated in `CONTACT_IDS` in `admin/src/lib/pages.ts` (a test checks every one is used by `main.js` and present in all three languages), and a save that removes one is refused. The "Last updated …" wording of the privacy page, per language, is in `STAMPS` there.
- **The Now page is data, not HTML.** `content/now/` is a bundle: `index.md` / `index.fr.md` / `index.it.md` carry only title, description and `type: "now"`; everything shown — `updated` date, a cover photo cropped wide, the intro, the rows (`logo`, `url`, `label`, `text`) and the `archive` by year — is in `content/now/now.json`, all three languages side by side (an empty language falls back to English), rendered by `layouts/now/single.html`. Text fields are inline Markdown. A row's `logo` is `icon:<name>` (line icons in `data/now_icons.json`, read by both the site's `now-icon.html` partial and the portal's picker), a `/img/…` site path, or a picture in the bundle. The portal's editor is `admin/src/routes/(app)/pages/now/` (it shadows `pages/[name]` for this one page); the file's shape and checks are `admin/src/lib/now.ts` (pure), the I/O `content/now.ts`. A save commits now.json, the front matter, uploaded pictures, and deletes bundle pictures nothing names any more. The link check, dead-link fixes, the "still true?" task and the Library all read now.json. Change the shape in the template and `lib/now.ts` together (`test/now.test.ts` checks they agree).
- **Homepage text in `hugo.toml`** — `quote`, `quoteAuthor`, `quoteArticle` under `[params]` and `description` under each `[languages.<lang>.params]` — is edited from Settings by the same line editor as the social links. The hero photo is replaced as a pair (`assets/img/hero.webp` + `hero.jpeg`, one commit), and the CV at whatever root `.pdf` `resumeUrl` names.
- **A draft can be shown by link, and that is the portal's one public read path besides sign-in.** `/preview/<token>` (and `/preview/<token>/img/<file>`) answer without a session, listed in `PUBLIC` in `auth/access.ts` and `INTENDED_PUBLIC` in `test/access.test.ts`. Safety rests on the 192-bit token (`previews.ts`, one live link per article, 7-day expiry, revoked on delete/rename or by "Stop sharing"), on the routes being read-only, noindex, uncached and script-free (own CSP and Referrer-Policy, which `hooks.server.ts` now leaves alone when an endpoint sets them), and on pictures coming only from that article's folder. What it shows is the autosave if there is one, else the saved article (`preview-link.ts`).
- **The newsletter is one list per language.** Resend's contacts are global and a list is a *segment*: `RESEND_SEGMENT_EN/FR/IT` (English defaults to the pre-language "General" list; French and Italian exist once their ids are set, made by `admin/scripts/resend-setup.mjs`). The signup form's language is signed into the confirmation link (`functions/lib/confirm.js`, claim `l`), and confirming files the address on that language's segment (or English when that list is not set up). The portal sends one broadcast per list (`newsletter-plan.ts` decides who gets what: own language if the article has a version, else nothing unless the English one is asked for; `newsletter-email.ts` writes the email in the language), schedules per-language `dispatches` (`schedule/plan.ts`; a retry sends only the lists not yet sent to), and moves a subscriber between lists from the Subscribers tab. Never send to a segment by guessing a language: a list without an id is simply not offered.
- **Backups are links, not features.** The repository is the site; `content/backup.ts` only builds GitHub's archive URL (Settings → Backup), with the repo's size from GitHub's API when deployed. The subscriber list (Resend) is the one thing in no repository, so it has a CSV download; `listSubscribers` reads every page of it (`integrations/paginate.ts`), because Resend returns 20 rows by default. Do not add a portal-built content zip: it would not fit the container's memory.
- **Scheduled publishing runs at one fixed morning**: 9:00 Paris time (articles) and 9:30 (newsletter). `PUBLISH_HOUR`/`PUBLISH_TZ` in `admin/src/lib/server/schedule/plan.ts` must match the cron schedule and timezone in `admin/scripts/create-container.sh`. Don't add more trigger runs: each wakes the container for ~15 minutes and September 2026 was billed past Scaleway's free tier because of exactly that (see `admin/DEPLOY.md`, "What it costs").
- **Site name and menu** (`title` above the first table, and each `[[languages.<l>.menus.main]]` block) are edited from Settings by the same line editor (`readTitle`/`writeTitle`, `readMenu`/`writeMenu` in `site-params.ts`): names and order only, never adding or removing a menu entry (a menu entry needs a page that exists). Order is written as weights 1…n into all three languages, so the menus cannot drift apart; the blocks keep their place in the file.
- **Footer social links** are `[params]` keys in `hugo.toml` (`linkedin`, `mastodon`, …), edited from the portal's Settings by `admin/src/lib/server/content/site-params.ts`, which rewrites only the quoted value on existing lines. The key list is duplicated in `SOCIALS` there and in `layouts/partials/footer.html` (lowercased, as Hugo reads param names); an empty value hides the icon. A new network needs its key in both, a line in `hugo.toml`, and an icon in `layouts/partials/social-icon.html`.
- **The portal's look is generated from the site**: `admin/scripts/sync-brand.mjs` derives its tokens, fonts, logo and the preview's stylesheet from `static/css/main.css`, `static/fonts/` and `static/img/logo.svg`. Those paths also redeploy the portal.
- **`data/gallery_*.json`** is rewritten by the portal in the existing hand-aligned format, and gallery cities get their `.fr.md`/`.it.md` stubs automatically.
- **`static/<key>.txt`** is the IndexNow key file; it must match `INDEXNOW_KEY` (see `admin/DEPLOY.md`).
- **What a Litlyx shareable link may read is Litlyx's decision, per endpoint** (`flag:allowShare` in its source): pages, referrers, countries, devices, browsers, systems, UTM tags, entry and exit pages, time on page, bounce rate, visit length and live visitors are open to it; custom events and raw exports are not. Each optional panel is fetched on its own (`loadExtras`), so an endpoint another Litlyx version lacks hides one panel, not the page. A new panel's parser belongs in `litlyx-parse.ts` and its shape should be checked against the real instance.
- **Resend's opens and clicks exist only if tracking is on for the sending domain**, and the privacy policy says it is off. The Sent tab always shows delivered, bounced, marked-as-spam and unsubscribed (pulled from `GET /broadcasts/{id}/recipients?type=…` when the tab opens, never by webhook, which would wake the container), and opens and clicks only if Resend returns any. Resend has deprecated its Audiences API (no removal date); the portal and `functions/newsletter.js` still use it, and both move together when it goes.
- **Google Search Console, PageSpeed and the health check follow the Bing pattern**: a disk cache, a result object instead of a throw, and "not connected" a state the page renders. Google reads as a service account with a read-only scope (`GSC_SERVICE_ACCOUNT_B64`, `GSC_SITE_URL`); the account's email must be added as a user of the property. The health check runs inside the existing morning trigger at most once every 20 hours — do not add trigger runs for it (see the scheduled publishing contract) — and is a daily look, not live monitoring.
- **Redirect stubs** written by `rename.ts` are read back by `content/redirects.ts` for the Redirects page, which flags ones pointing at deleted articles, chains, and addresses an article uses again. Keep the stub shape (`type`, `url`, `redirect_to`) in step with `layouts/redirect/single.html`.

**Security model:** passkeys only (WebAuthn, RP ID `admin.loconsole.eu`). Access is **deny-by-default** in `admin/src/hooks.server.ts`: a request without a session only reaches paths in the allow-list in `admin/src/lib/server/auth/access.ts`, so a new route is protected the moment it exists. Don't move this into layout `load` functions — SvelteKit doesn't run them before form actions, which is exactly how the first version left every action open. `admin/test/access.test.ts` walks the route tree and fails if anything new becomes public.
